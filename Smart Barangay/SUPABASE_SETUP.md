# Supabase Setup Guide

This guide connects SmartBarangay to a Supabase project and stores resident, document, concern,
announcement, and weather-alert records in PostgreSQL. The Flask server is the only component
that talks to Supabase; browser JavaScript calls the Flask API and never receives the service-role
key.

## 1. Create a Supabase project

1. Open [supabase.com](https://supabase.com) and sign in.
2. Select **New project**.
3. Choose an organization, enter `Smart Barangay` as the project name, and create a strong database password.
4. Choose a region near your users.
5. Click **Create new project** and wait for the project to finish provisioning.

## 2. Set up authentication and roles

1. Run the complete [supabase_schema.sql](supabase_schema.sql) file in Supabase **SQL Editor**.
2. Open **Authentication → Providers → Email** and enable Email provider.
3. Open **Authentication → Users → Add user**, create the first admin, and enable **Auto Confirm User**.
4. Copy the new user's UUID and create its role profile in SQL Editor:

```sql
insert into public.profiles (id, email, full_name, role)
values ('PASTE-AUTH-USER-UUID-HERE', 'admin@example.com', 'System Administrator', 'admin');
```

Only an admin can register later resident and barangay official accounts from **Settings → User Accounts**. When creating an official, select a department; officials only receive concern records for their assigned department.

For local development, keep `FLASK_SESSION_SECURE=false`. Set it to `true` when Flask is served over HTTPS.

## 3. Create the residents table

1. In the Supabase dashboard, open **SQL Editor**.
2. Click **New query**.
3. Paste the SQL below.
4. Click **Run**.

```sql
create table if not exists public.residents (
  id bigint generated by default as identity primary key,
  resident_id text generated always as ('RES-' || lpad(id::text, 3, '0')) stored unique,
  full_name text not null,
  address text not null,
  household text not null default 'UNASSIGNED',
  age integer not null check (age between 1 and 120),
  gender text not null check (gender in ('Female', 'Male', 'Other')),
  status text not null default 'Pending' check (status in ('Verified', 'Pending', 'Inactive')),
  resident_since date not null default current_date,
  created_at timestamptz not null default now()
);

alter table public.residents enable row level security;

-- The Flask server uses the service-role key, so it can access this table.
-- These policies are useful if you later read the table from a browser client.
create policy "Residents can be read by authenticated users"
on public.residents for select
to authenticated
using (true);

create policy "Authenticated users can create residents"
on public.residents for insert
to authenticated
with check (true);

insert into public.residents (full_name, address, household, age, gender, status, resident_since) values
  ('Maria Santos', 'Purok 3, Blk 4 Lot 2', 'HH-0042', 34, 'Female', 'Verified', '2018-03-12'),
  ('Juan dela Cruz', 'Purok 1, Blk 2 Lot 8', 'HH-0015', 52, 'Male', 'Verified', '2010-07-22'),
```

## 4. Apply the database schema

The full multi-screen schema is in [supabase_schema.sql](supabase_schema.sql). After creating `residents`, open that file, copy its contents into a new Supabase SQL Editor query, and click **Run**. It creates and seeds:

- `documents` for document requests
- `concerns` for community concerns
- `announcements` for public announcements
- `weather_alerts` for emergency advisories

The schema also adds official departments, expanded report/document statuses, document pickup date/time
fields, and the applicant/business information captured for certificate requests:

- `documents.applicant_address`
- `documents.applicant_contact`
- `documents.applicant_date_of_birth`
- `documents.applicant_place_of_birth`
- `documents.applicant_civil_status`
- `documents.business_name`
- `documents.business_address`

Re-run it after upgrading an existing project so the `alter table` migrations are applied.

The application routes these tables through:

- `/api/dashboard` for dashboard metrics and charts
- `/api/residents` for resident registration and updates
- `/api/documents` for resident requests and staff processing
- `/api/documents/<id>/certificate.pdf` for approved/resolved certificate downloads
- `/api/concerns` for resident reports and official status updates
- `/api/announcements` for public announcements
- `/api/weather-alerts` for emergency broadcasts
- `/api/reports/<name>` for CSV exports (`residents`, `documents`, `concerns`,
  `demographics`, `weather-alerts`, or `audit`)

Run the schema before opening those navigation pages. The migration statements at the end of
`supabase_schema.sql` are safe to run against an existing installation and add the fields used
by the current dashboards, including document `purpose`, concern `description`, weather-alert
`author`, announcement `description` and author email, indexes, and idempotent seed data.

After running the migration, verify that the certificate-request fields exist:

```sql
select column_name, data_type
from information_schema.columns
where table_schema = 'public'
  and table_name = 'documents'
  and column_name in (
    'applicant_address',
    'applicant_contact',
    'applicant_date_of_birth',
    'applicant_place_of_birth',
    'applicant_civil_status',
    'business_name',
    'business_address'
  )
order by column_name;
```

Only requests with `Approved` or `Resolved` status can be downloaded as a PDF by an administrator
or barangay official. The generated certificate contains the applicant information, request number,
purpose, issue date, processor, and an authorized-official signature/seal area. The PDF is a formal
system-generated template and still requires the authorized signature and official barangay seal
before release.

## 5. Configure credentials and sessions

1. In Supabase, open **Project Settings**.
2. Open **API**.
3. Copy **Project URL**.
4. Copy the **service_role** key under **Project API keys**.
5. Do not put the service-role key in HTML, JavaScript, GitHub, or any browser-visible file. It bypasses Row Level Security and belongs only on the Flask server.

Open PowerShell in the project folder and install the dependencies:

```powershell
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Copy `.env.example` to `.env`:

```powershell
Copy-Item .env.example .env
```

Open `.env` and replace the placeholder values:

```env
SUPABASE_URL=https://your-project-ref.supabase.co
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
```

Keep `.env` private. Add it to `.gitignore` before committing:

```gitignore
.env
.venv/
__pycache__/
```

## 6. Start and verify the app

```powershell
python main.py
```

Open `http://127.0.0.1:5000`, sign in, and verify the Dashboard, Residents, Documents,
Concerns, Announcements, Weather & Alerts, and Reports pages with an account that has the
appropriate role. The health endpoint reports whether the server has a usable service key:

```powershell
Invoke-WebRequest http://127.0.0.1:5000/health | Select-Object -ExpandProperty Content
```

It returns HTTP 200 only when the Supabase URL and server-side key are usable. A publishable
(`sb_publishable_...`) key may be used for limited reads, but writes and account administration
require `SUPABASE_SERVICE_ROLE_KEY` and the health endpoint will remain degraded until it is set.

You can also test the API:

```powershell
Invoke-WebRequest http://127.0.0.1:5000/api/residents | Select-Object -ExpandProperty Content
```

A successful response looks like:

```json
{"configured":true,"data":[{"resident_id":"RES-001","full_name":"Maria Santos"}]}
```

## 7. How syncing works

- The browser asks Flask for `GET /api/residents` when the Residents page opens.
- The dashboard asks Flask for `GET /api/dashboard` and calculates resident totals, unique households, registration history, verification counts, and age groups from the same table.
- Flask uses `supabase_repository.py` and the server-only Supabase key to query `public.residents`.
- Add Resident sends a `POST /api/residents` request to Flask; the resident view also uses
  `PATCH /api/residents/<id>` for edits.
- Residents submit document requests and concern reports through the same Flask API. Officials
  can create staff requests, update document/concern statuses, publish announcements, and
  broadcast weather alerts according to their role.
- After each mutation, the relevant list and dashboard metrics are reloaded from Supabase.
- The browser does not contain sample resident or request records; an unavailable API is shown as
  an empty/unavailable state with an error toast.
- Barangay official views are filtered by the official's assigned department on the server.

## 8. Production deployment checklist

1. Run `supabase_schema.sql` in the target Supabase project and verify the migration statements
   completed successfully.
2. Configure `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and a long random
   `FLASK_SECRET_KEY` as hosting-provider secrets. Never expose the service-role key in a
   template, JavaScript bundle, repository, or client-side environment variable.
3. Set `FLASK_SESSION_SECURE=true` when the app is behind HTTPS. Set `FLASK_HOST=0.0.0.0`
   and provide the platform's `PORT`.
4. Run the application with the included production WSGI entry point:
   `waitress-serve --listen=0.0.0.0:$PORT wsgi:app` (or `python wsgi.py`), not Flask's
   development server.
5. Call `/health` from the deployment and require HTTP 200 before accepting traffic.
6. Create the first confirmed Supabase Auth user, insert its admin profile, then use the admin
   dashboard to register officials and residents.

## 9. Deploy on Vercel

The project is configured for Vercel's Python runtime. Vercel loads the Flask `app` exported from
`api/index.py`, which imports the application from `main.py`, installs dependencies from
`requirements.txt`, and serves the application as a serverless function. Static assets are stored
under `public/static/` for Vercel's static delivery. The rewrite in `vercel.json` sends application
routes to the Flask function while allowing Vercel to serve static assets directly.

### Option A: Deploy from the Vercel dashboard

1. Put this project in a GitHub, GitLab, or Bitbucket repository. Confirm that `.env` is not
   committed.
2. Open [Vercel](https://vercel.com) and select **Add New → Project**.
3. Import the repository and select the folder containing `main.py` as the project root.
4. Leave the framework preset as **Other** if Vercel does not automatically select Python.
5. Open **Settings → Environment Variables** and add these variables for **Production**, **Preview**,
   and **Development**:

   ```text
   SUPABASE_URL
   SUPABASE_SERVICE_ROLE_KEY
   FLASK_SECRET_KEY
   FLASK_SESSION_SECURE=true
   FLASK_DEBUG=false
   ```

   Use the Supabase server-side `service_role` or `sb_secret_...` key for
   `SUPABASE_SERVICE_ROLE_KEY`. Never use the `sb_publishable_...` key for this variable, and
   never expose the server-side key to browser code.
6. Click **Deploy**.
7. After deployment, open `https://YOUR-VERCEL-DOMAIN/health`. Continue only when it returns
   HTTP 200 and `"status":"ok"`.
8. Open the deployment URL, sign in, and test resident requests, concern reports, document
   processing, announcements, weather alerts, and reports.

### Option B: Deploy with the Vercel CLI

Install the CLI and log in once:

```powershell
npm install --global vercel
vercel login
```

From the folder containing `main.py`, link the project and add secrets without putting them in
the repository:

```powershell
vercel link
vercel env add SUPABASE_URL production
vercel env add SUPABASE_SERVICE_ROLE_KEY production
vercel env add FLASK_SECRET_KEY production
vercel env add FLASK_SESSION_SECURE production
vercel env add FLASK_DEBUG production
```

When prompted, paste each value directly into the terminal. Do not paste any private key into
chat. Use `true` for `FLASK_SESSION_SECURE` and `false` for `FLASK_DEBUG`, then deploy:

```powershell
vercel --prod
```

If preview deployments are needed, add the same variables to the `preview` environment and run
`vercel` without `--prod`.

Vercel does not run `wsgi.py` or Waitress. Those are retained for local and traditional
server deployments; Vercel loads the Flask `app` from `main.py` directly.

## Troubleshooting

- **`Supabase is not configured`**: confirm the file is named `.env`, is beside `main.py`, and both variables have values.
- **401 or permission errors**: confirm `SUPABASE_SERVICE_ROLE_KEY` is the `service_role` key, not an expired or incomplete value.
- **RLS error when saving residents**: a `sb_publishable_...` key is not allowed to bypass Row Level Security. Add the `service_role` key as `SUPABASE_SERVICE_ROLE_KEY` in `.env`, then restart Flask. Never put this key in browser JavaScript or commit it.
- **Table or column not found**: run the complete `supabase_schema.sql` migration in the correct
  Supabase project, including the statements after the seed data.
- **Duplicate sample rows**: the insert statements are seed data. Run them once, or delete duplicate rows from **Table Editor > residents**.
- **Unstyled page or `/static/style.css` returns 404**: stop any older Flask process and restart
  it from the folder containing `main.py`. The current stylesheet is
  `public/static/style.css`; after changing the deployment layout, an already-running process
  still uses its old static-folder setting. For Vercel, set the project Root Directory to the
  folder containing `main.py` and `vercel.json`, then deploy again.
